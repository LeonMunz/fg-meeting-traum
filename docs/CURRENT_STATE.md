## Work Items

- **IMPLEMENTED** — single canonical `WorkItem` model; every Work Item belongs to exactly one Project.
- **IMPLEMENTED** — configurable Project definitions: `WorkItemTypeDefinition`, `WorkItemStatusDefinition` (fixed semantic category: `todo`/`in_progress`/`review`/`done`), `WorkItemLabelDefinition`.
- **IMPLEMENTED** — stable semantic kind for canonical Work Item types (`WorkItemTypeDefinition.kind`, migration `projects/0006`): the display `name` is presentation metadata and is never an authoritative source for semantic kind, including during data migration; the semantic concept is a stable machine-readable `kind` (`task`/`epic`/`milestone`/`deliverable`), never inferred from the name at runtime. The kind is system-assigned only — the four canonical default definitions receive their kind at Project creation (`Epic→epic`, `Milestone→milestone`, `Deliverable→deliverable`, `Task→task`), and custom types created by owners carry no kind (`null`). Migration `projects/0006` adds the nullable `kind` column and performs NO data backfill: the only legacy machine-readable type values ever persisted lived on the Work Item (`work_items/0001` `type` choices) and were dropped by `work_items/0004` without ever being stored on the definitions, and no definition column records which legacy value a row was created from (or that the system, as opposed to an owner, created it), so there is NO machine-readable provenance identifying the canonical origin of pre-existing rows; classifying by any combination of `name`/`order`/`active`/project age would attribute semantics from mutable presentation/configuration state (an owner-created custom type named exactly `Task` would be misclassified, and a renamed canonical default lost), so every pre-existing definition keeps `kind = null` — false negatives deliberately accepted, false semantic attribution refused. Canonical kinds are assigned only going forward, at Project creation. The kind is exposed read-only in the Project Work Item configuration payload (`kind` per type) and is not writable: client-supplied `kind` on type create/update is ignored (no type-kind picker, no type-management UX change). Renaming a canonical definition never changes its kind; authorization for the configuration endpoints is unchanged. Canonical reference: `docs/domain/foundation.md` §3a.1 (Semantic Kind) + invariant 26.

## Activity

Canonical domain reference: `docs/domain/activity.md`.

- **IMPLEMENTED** — Activity event foundation (persistence/domain only — no Activity API, no Home Activity rail, no feed rendering; Activity is an awareness/history stream, not a notification inbox). Activity events are the canonical persisted concept `audit_history.AuditEvent` (append-only, no update/delete path), recorded through `record_audit_event` **inside the same logical transaction** as the domain mutation: a rollback never leaves an orphaned event and a committed mutation always has its event (pinned by simulated post-mutation failure tests for create and update).
- **IMPLEMENTED** — Work Item event slice: one event per logical operation (domain-level action boundary, deliberately NOT one event per changed column) — `work_item.created` and `work_item.updated` with a structured, ID-based `data["changes"]` diff. The required action boundaries are reconstructable from the persisted event: **status changed** (`statusDefinition` from/to refs), **completed** — semantically distinct from an ordinary status change because the stored status summary now carries the fixed semantic `category` (`todo`/`in_progress`/`review`/`done`), so a transition into `done` (which drives the server-managed `completed_at`) is marked `to.category == "done"` with no join back to the StatusDefinition; a transition out of `done` is an ordinary status change, **assignee changed** (`assignees.added`/`assignees.removed` user refs), **due date changed** (`dueDate` from/to, including clearing to null). A no-op update records no event. Board drag/drop reuses the same contract (cross-column move = one `work_item.updated` with the status transition; pure within-column reorder = no event).
- **IMPLEMENTED** — structured-semantics rule: `event_type` is a stable machine code and `data` stores IDs + fixed enums (rendered names are display convenience, never the source of truth) — a later projection can answer WHO (actor FK) / WHAT (event type + structured changes) / WHICH (WorkItem FK or Meeting FK) / WHERE (Project + Research Group scope FKs) / WHEN (`created_at`).
- **IMPLEMENTED** — Meeting event slice (second real object type on the same `AuditEvent` concept; no second event table): one event per logical Meeting operation — `meeting.created` (both `create_meeting` and `create_meeting_from_series`; Series section snapshots and the default Agenda Section are internal structure, not events), `meeting.rescheduled` (a real `scheduled_at` change in one `update_meeting` = one event with structured `scheduledAt` from/to as UTC ISO-8601; a title-only or same-value update records no event — the title is not a tracked aspect), `meeting.completed` (`end_meeting` only; structured `endedAt`; Start/Reopen are not recorded), `meeting.agenda_item_added` (`create_meeting_item`; item id+title, internal `position` writes never appear), and `meeting.follow_up_scheduled` (`schedule_meeting_item_follow_up`; anchored to the TARGET Meeting with its Research Group/Project scope, structured `sourceMeeting`/`sourceItem`/`targetSection`/`targetItem` refs plus a stable flat `data["sourceMeetingId"]`; the internally materialized target item records no separate `agenda_item_added` event; an idempotent retry records no second event). All are recorded inside the same `transaction.atomic()` block as the Meeting mutation (pinned by simulated post-mutation failure tests for create, reschedule, complete, and follow-up); `update_meeting` is now transactional for that guarantee.
- **IMPLEMENTED** — Activity authorization rule: an Activity entry about an object is visible iff the user can read that object today (never a privacy bypass). Proven by the existing `GET /api/work-items/{id}/history/` enforcing the identical read rule as the Work Item itself (ProjectMembership owner/member/viewer + current ResearchGroupMembership; group admin without Project membership gets a non-leaking 404).
- **IMPLEMENTED** — permission-safe aggregate Activity read API `GET /api/activity/` (authenticated; Work Item slice events `work_item.created` / `work_item.updated` plus Meeting slice events `meeting.created` / `meeting.rescheduled` / `meeting.completed` / `meeting.agenda_item_added` / `meeting.follow_up_scheduled` plus Project slice events `project.member_assignments_resolved` / `project.ownership_resolved_for_offboarding` / `project.archived` / `project.restored` / `project.deleted` plus Research Group slice event `research_group.member_offboarded`). Read-time authorization: a Work Item event is returned only if the requester can read the affected Work Item today through the canonical Project read boundary — the identical rule of Work Item reads and per-Work-Item history (a Research Group admin without Project membership sees no private Project Activity); a Meeting event is returned only if the requester can read the affected Meeting today through the canonical `MEETING_READ` rule (creator-or-explicit-participant; group/Project membership, ownership, or admin status alone never grants Meeting Activity visibility); a `meeting.follow_up_scheduled` event is returned only while the requester can read BOTH the source and the target Meeting today, so target-only readability never leaks source Meeting metadata (the source reference is filtered in the database via the stable `data["sourceMeetingId"]` key); a Project event is returned only if the requester can read the affected Project today through the identical canonical Project read boundary (current ProjectMembership owner/member/viewer + current ResearchGroupMembership — the identical rule of Project reads; a Research Group admin without Project membership sees no private Project Activity either); archiving is not deletion — an archived Project keeps normal read authorization, and the archive state itself neither grants nor revokes; a `project.deleted` event (Project FK nulled by the deletion) is durably persisted but never returned — it fails closed and is never authorized from the retained research_group scope, actor, subject user, or payload; a Research Group event is returned only while the requester can read the affected Research Group today through the identical canonical group read rule (current ResearchGroupMembership — both the member and the admin role grant `GROUP_READ`, the identical rule of Research Group reads); losing group membership immediately removes the historical Research Group events, and the event's `subject_user` (the offboarded member) never grants access — subject identity retains nothing; Research Group deletion is not supported (the event's `research_group` FK is NOT NULL / RESTRICT), so a retained Research Group event always references an existing group whose current read authorization is evaluable; participant removal through the normal domain path removes matching historical events from the feed immediately. The permission filter runs in the database before bounded pagination (`?limit=` 1..100, default 50; `?offset=` non-negative with a hard bound; invalid → 400) on a deterministic reverse-chronological ordering (`-created_at`, `-id`), so inaccessible events leak no title, actor, context, event data, existence, count, or page behavior; the response is a bare page with no total count. The feed projection is structured (event id / machine `eventType` / `createdAt`, the existing audit/history actor representation, `subjectUser` — the user an operation acted upon (for Project events the resolved member / final owner; for `research_group.member_offboarded` the offboarded member), same user-ref representation as actor, null for Work Item / Meeting events and for Project events without one (never fabricated; event context, never an authorization input), affected Work Item id + current title or affected Meeting id + current title with the non-matching identity pair null, Project/Research Group context — null Project for group-scoped Meetings, the affected Project itself for Project events, the event's own Research Group with null Project for Research Group events — and the structured `changes` payload whose Work Item semantic `category` distinguishes a completion via `to.category == "done"`; for Project events `changes` carries exactly the allowlisted persisted payload keys of that event type, for Research Group events the allowlisted offboarding summary keys — never the raw `AuditEvent.data`); events of a hard-deleted Work Item, Meeting, or Project leave the feed while staying durable in the database (FK nulled via `SET_NULL`). The feed issues no per-event relation queries: every relation the serializer reads (`select_related` actor / subject user / Work Item / Project / Research Group / Meeting / the Meeting's Project / the Meeting's own Research Group / the event's own Project and its Research Group / the event's own Research Group) is eager-loaded on the page queryset, so the per-request query count is constant in the page's row count (one page query plus the session/authentication queries shared by every authenticated request).
- **IMPLEMENTED** — Activity feed fail-closed hardening for `meeting.follow_up_scheduled` source references: the stored `data["sourceMeetingId"]` is type-checked in the database before any numeric conversion (jsonb type check, then an arbitrary-precision numeric comparison against the readable-Meeting subquery), so a persisted malformed reference (missing key, JSON null, string, boolean, object, array, or non-integral number) excludes exactly that event — `GET /api/activity/` still responds successfully, no malformed row can fail the request or be coerced into another Meeting ID, and the dual-readability rule (source AND target readable today) is unchanged for valid references.
- **IMPLEMENTED** — Project and Research Group audit event persistence (pre-existing; predates the aggregate Activity feed work): recorded through the same canonical `record_audit_event` into `audit_history.AuditEvent` inside the same transaction as the domain mutation. Project events (`project` FK = the affected Project): `project.member_assignments_resolved` (assignment resolution during membership role change, membership removal, and Research Group offboarding), `project.ownership_resolved_for_offboarding` (ownership transfer for the offboarded final owner), `project.archived` (manual archive and Research Group offboarding archive), `project.restored`, and `project.deleted` (empty archived Project; the event is persisted before the Project row is deleted, so its `project` FK is nulled afterward). Research Group event (no `project` FK): `research_group.member_offboarded`. The Project events are durably persisted and **ARE** currently returned by `GET /api/activity/` under the read-time Project authorization rule above (Project Activity feed projection); the Research Group event **IS** currently returned by `GET /api/activity/` under the read-time group read rule above (Research Group Activity feed projection: visible only while the requester can currently read the group — `GROUP_READ`, both member and admin roles — and the event's `subject_user`, the offboarded member, never grants access; the structured offboarding summary is projected through the same allowlist mechanism). The nullable `subject_user` FK is set only by these pre-existing events, to the user the operation acted upon (the offboarded member, the member whose role/membership/assignments were resolved, the offboarded final owner); Work Item and Meeting events do not set it. Canonical reference: `docs/domain/activity.md` §4b.
- **IMPLEMENTED** — Activity feed domain filter (backend/API contract; now consumed by the Home Activity rail's compact filter control — see the Home frontend entry below): `GET /api/activity/` accepts an optional `?domains=` query parameter — a comma-separated list drawn from exactly the four approved Activity domains `work_item` / `meeting` / `project` / `research_group` (the public filter contract; arbitrary `event_type`-prefix filtering is never exposed to the client). When `domains` is absent (or empty) the feed is unchanged, and OR-ing all four domains equals the unfiltered feed. Multiple values use OR semantics; duplicate valid values normalize harmlessly (a set); stray empty segments (e.g. `meeting,`) are ignored. A value that names no domain (e.g. `domains=,`) or that contains any unknown domain (e.g. `meeting,banana`) is rejected with HTTP 400 (`{"error": ...}`) before any query runs, so an invalid filter never partially executes. A persisted event's domain is its `event_type` prefix (`work_item.*` → work_item; `meeting.*` → meeting, including `meeting.follow_up_scheduled`; `project.*` → project; `research_group.*` → research_group). The filter narrows the permission-filtered queryset in the database BEFORE the bounded `?limit=`/`?offset=` pagination slice — never an in-memory filter over an unfiltered page — so a page always holds the newest events of the selected domains. It only NARROWS otherwise-visible events: each domain branch already encodes that domain's current read authorization, so the filter never widens visibility, grants access, or changes the read-time authorization rules (current access determines visibility, stored scope never grants, and revoked access / deleted / unverifiable objects fail closed as before). Global ordering (`-created_at`, `-id`) and the bare-page no-total-count contract are unchanged; no per-domain regrouping or new sort is introduced. Read-only contract addition: no model/migration change, no new dependency. Covered by `apps/api/audit_history/tests_activity_feed_domains.py`.

## Recurring Meetings (recurrence core)

- **IMPLEMENTED** — recurring-meeting core as a persisted domain model (domain + migration only; a read-only occurrence READ API is now implemented — see below; creation/editing remain domain-only, no UI): `meetings.MeetingRecurrence` (migration `meetings/0014`) stores a V1 recurrence schedule — `frequency` (`daily` / `weekly` / `monthly`), positive `interval`, an optional sorted ISO-weekday set (`0 = Monday … 6 = Sunday`) for weekly schedules only, `start_date` (local calendar date of the first occurrence), `local_time` (configured local wall-clock time), IANA `timezone_name`, and an end mode — `no_end`, inclusive `end_date`, or `count` (total occurrences, INCLUDING the first; `end_date` and `count` mutually exclusive). The schedule carries the existing Meeting ownership/context shape (Research Group, `group` / `project` scope, optional Project, `created_by`, timestamps). DB check constraints enforce scope/Project consistency, `interval >= 1`, end-mode field consistency, `end_date >= start_date`, and empty weekdays for non-weekly frequencies. Creation goes through the service `create_meeting_recurrence`, which reuses the canonical scoped Meeting write rule and rejects: unsupported frequencies, `interval <= 0`, weekly without valid weekdays, a weekly start date whose weekday is not in the pattern, weekdays on non-weekly schedules, non-IANA timezones, `count <= 0`, simultaneous `count` + `end_date`, `end_date` before `start_date`, and any field incompatible with the selected end mode.
- **IMPLEMENTED** — bounded occurrence expansion as a read-only domain operation (`expand_meeting_recurrence_occurrences`, pure engine in `meetings.recurrence`, stdlib `zoneinfo`; no new dependency): the operation ALWAYS requires an explicit bounded, timezone-aware window — there is no unbounded "return every occurrence" operation by API shape. Expansion calculates occurrences deterministically in the schedule's local wall-clock time using its IANA timezone, preserves the configured local clock time across DST transitions (the UTC instant shifts with the offset), respects daily/weekly/monthly intervals (weekly weeks anchored at the start date's week), treats the end date as inclusive, treats the count as total meetings including the first (occurrences before the window consume the count), skips nonexistent calendar dates for monthly schedules (never shifting to the month end), and never returns occurrences outside the requested window (the window is converted into the stored timezone before filtering). Each occurrence is a value — not a model row — carrying the original local wall-clock start, the DST-correct aware start, and a stable deterministic identity (UUIDv5 over schedule id + original local start + timezone) suitable as the immutable original-start identity for future override support; repeated expansion of the same schedule/window yields identical values and identities. Expansion creates no `Meeting` rows and stays independent of persisted concrete Meetings.
- **IMPLEMENTED** — occurrence → concrete Meeting materialization as ONE canonical, idempotent domain operation (`materialize_meeting_recurrence_occurrence`; domain + migration, now exposed through the idempotent HTTP materialization action below): materializes ONE validated calculated occurrence into exactly one normal concrete `Meeting` — a parallel recurrence-specific Meeting type does NOT exist. The Meeting inherits the recurrence's Research Group / scope / Project, starts `upcoming`, is created by the actor, is initialized standalone-style (one default `Agenda` Section + creator participant + one `meeting.created` event), and carries no `series` (Recurrences have no Meeting Template association in V1, so nothing is snapshotted from a Template; the materialized Meeting owns its own persistent state like any other Meeting). The immutable occurrence provenance is persisted on `Meeting` (migration `meetings/0015`; ordinary Meetings are unchanged): nullable `recurrence` FK (RESTRICT) + nullable `original_scheduled_at` (the occurrence's original scheduled start as an aware instant — in the recurrence's stored timezone it is the original wall-clock start, and the canonical Slice-1 UUIDv5 occurrence identity is derived from it; it NEVER depends on `scheduled_at`). `scheduled_at` is initialized to the occurrence's original start but remains the Meeting's own editable planned time: a later override may move it without redefining the original occurrence identity (the persistence contract for moving is in place; moving itself is deferred). DB invariants: the two provenance fields are paired (both set or both NULL, check constraint) and `(recurrence, original_scheduled_at)` is UNIQUE (NULL unconstrained) — one concrete Meeting per occurrence per recurrence. Idempotency: the first call creates the Meeting, repeated calls return/reuse the existing row (first creation's title/state wins); the unique constraint makes duplicates impossible even when two materializations race (the losing transaction rolls back and the winner's row is returned). The candidate is validated before any write: it must carry the canonical occurrence identity for EXACTLY this recurrence AND actually be produced by the rule within its end-date / count contract — forged identities, occurrences from other recurrences, off-rule wall-clock times/dates, and occurrences before the start or beyond the end are rejected, so callers cannot invent arbitrary recurrence ids or original starts. Creating or expanding a recurrence still creates ZERO `Meeting` rows (no eager materialization, ever).

## Account Invitations

Canonical domain reference: `docs/domain/account-invitations.md`.

- **IMPLEMENTED** — global account invitation foundation: `accounts.AccountInvitation` (stable `public_id` UUID, inviter, normalized invited email, one-way SHA-256 token digest, lifecycle state, created/expiry/accepted/revoked timestamps). The raw token is cryptographically random (`secrets`), single-use, **never persisted**, never in `repr`, never in list serialization or logs; it is returned exactly once by the creation response (e-mail delivery deferred).
- **IMPLEMENTED** — API (browser-authenticated, real CSRF enforcement, active accounts only): `GET /api/account-invitations/` (own invitations with effective state, no secrets, other inviters never listed), `POST /api/account-invitations/` (201 + raw token once; `400` invalid email), `POST /api/account-invitations/{publicId}/revoke/` (own + effectively pending only; non-leaking 404), `POST /api/account-invitations/accept/` (existing-account flow: resolves token by digest, requires normalized authenticated-user email == invited email, atomically sets `accepted` + `accepted_at` + `accepted_by`; 404 unknown/terminal, 410 expired, 400 mismatch).
- **IMPLEMENTED** — canonical normalization: trim + lowercase (shared helper); stored emails are normalized; User email storage format intentionally unchanged (no User-email uniqueness introduced).
- **IMPLEMENTED** — lifecycle centralized in the service layer: `pending → accepted | revoked | expired`; terminal states never reactivate; exactly 7-day lifetime; effective expiry (a pending row at/past `expires_at` behaves as expired everywhere and is persisted as `expired` by state-evaluating operations; no scheduler).
- **IMPLEMENTED** — existing-account guard on invitation creation: `POST /api/account-invitations/` for a normalized email that already belongs to a User (canonical trim + lowercase lookup shared with registration; active or inactive) is rejected with `409` + stable code `account_exists` before any token is generated or invitation is written; it takes precedence over `pending_invitation_exists` and creates no memberships. Already-existing invitation records for account emails are still redeemed through the existing preview/acceptance/registration flows (the guard restricts new creation only).
- **IMPLEMENTED** — duplicate-pending rejection (non-account emails): creating for a normalized email that has an effective pending invitation fails deterministically (`409`, stable code `pending_invitation_exists`, neutral message) and leaves the existing invitation and its token completely unchanged (no replacement, no revocation, no token/expiry/timestamp change); the existing invitation remains fully usable. Expired/revoked invitations never block: an effectively expired persisted-PENDING row is transitioned to `expired` by the creation operation, and the new invitation gets a fresh cryptographically random token with the normal 7-day expiry.
- **IMPLEMENTED** — structural invariants: unique `public_id`, unique `token_digest`, and a partial unique index limiting to one `pending` row per normalized email (migration `accounts/0003`).
- **IMPLEMENTED** — concurrency (real PostgreSQL row locks / constraints, threaded tests): concurrent acceptance of one token leaves exactly one `accepted` transition with `accepted_by` set once; concurrent creation for one normalized email leaves exactly one pending invitation and exactly one usable token — the losing creation fails deterministically with `pending_invitation_exists` (partial unique index serializes the inserts; the empty-row race resolves into the duplicate rejection).
- **IMPLEMENTED (guarantee, pinned by tests)** — acceptance creates no User and no `ResearchGroupMembership` / `ProjectMembership`; the token grants no access to any ResearchGroup, Project, Work Item, or Meeting (authentication ≠ membership; deny-by-default authorization untouched).
- **IMPLEMENTED** — invite-only registration redeems a valid pending invitation into exactly one new account: `POST /api/auth/register/` (`{token, username, password}`; a client-supplied `email` is rejected fail-closed) atomically creates the normalized-email `User` and marks the invitation `ACCEPTED` in one transaction bounded by the invitation row lock, then authenticates a normal revocable session. No public signup, no membership, no permissions; an existing (incl. inactive) matching normalized email blocks signup and leaves the invitation pending. Real Postgres concurrency coverage proves one token yields exactly one account. Canonical reference: `docs/domain/account-registration.md`.
- **IMPLEMENTED** — non-consuming invitation preview: `POST /api/auth/registration-invitation/` (`{token}`) reports whether a token is effectively pending (invited email, expiry, `accountExists`) without consuming it, without authenticating, and without disclosing the email for a terminal token (persists an effective `EXPIRED` transition).
- **IMPLEMENTED** — non-consuming registration password policy: `POST /api/auth/registration-password-policy/` (`{token, username, password}`; a client-supplied `email` is rejected fail-closed) evaluates the candidate password with exactly the configured Django `AUTH_PASSWORD_VALIDATORS` (via `get_default_password_validators()`) against the same transient candidate identity registration uses (client username + invitation-authoritative email) and returns `{valid, requirements: [{code, label, satisfied}], accountExists}` using Django's stable validation codes and each validator's configured help text. Strictly read-only (no row locks, no invitation lifecycle persistence — an effectively expired PENDING invitation is reported `expired` while remaining PENDING), no User/membership creation, CSRF-protected like register/preview; failed registration now returns the same `requirements` array (`{code, error, requirements}`). Canonical reference: `docs/domain/account-registration.md` §13a.
- **IMPLEMENTED** — frontend live password-policy validation in the Create Account flow: the new-account form evaluates the in-progress candidate through `POST /api/auth/registration-password-policy/` (debounced 300 ms on username/password changes, with a latest-request guard so stale responses never overwrite a newer candidate). The guidance block is hidden while Password is empty; once a value exists it renders only the authoritative verdict for the CURRENT candidate as compact 11 px/16 px rows with 14 px icons (6 px row gap) — a single “Checking password requirements…” line while the candidate is being checked, and a verification-error line (no stale rows) when the check fails. The four canonical validator codes render concise user-facing copy (“At least 8 characters”, “Not a commonly used password”, “Not entirely numeric”, and — failed only — “Password is too similar to your personal information.”); raw Django help text is never shown for them, and an unknown future code falls back to the backend-provided label so it is never silently hidden. A satisfied similarity rule renders no row (visible or accessible); a failed similarity rule renders a concise danger error row. State is carried by icon plus visually-hidden “Satisfied.”/“Not satisfied.” text — visible copy never appends state words — and the password field gets a danger state only when the authoritative result for the current candidate is invalid. The backend remains the sole source of truth for rules and verdicts (no validator logic is reproduced in the frontend), a failed live check keeps the button disabled without optimistic success, and a final registration `password` rejection reconciles its authoritative `requirements` into the live display. The form renders in a fixed 380 px content column (24 px page gutters outside the box), the password inputs reserve a 72 px trailing band, and the app’s 32 px reveal button sits in its own slot offset from the far-right band used by browser-native credential controls (no password-manager functionality is disabled).
