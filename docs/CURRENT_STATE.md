- **IMPLEMENTED** — runtime-owned configuration only: required substitutions for `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` (first-initialization only — an already-initialized volume keeps its existing cluster and credentials), `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, and `DJANGO_CSRF_TRUSTED_ORIGINS`, plus the fixed internal contract `DJANGO_SETTINGS_MODULE=config.settings_production`, `POSTGRES_HOST=db`, `POSTGRES_PORT=5432` on `api`. `deploy/.env.example` contains placeholder names only; `deploy/.env` stays git-ignored via the root `.env` / `.env.*` rules; no real values live in the repository.

API health is liveness only; DB readiness is represented separately by the db healthcheck.
- **IMPLEMENTED** — gateway Caddyfile override: `deploy/Caddyfile` is mounted read-only over `/etc/caddy/Caddyfile` inside `web`, preserving the proven static contract (real fingerprinted assets under `/assets/*` with `public, max-age=31536000, immutable`; matcher-less SPA fallback with the revalidation-friendly `no-cache` document) while replacing the deliberate image-level `/api` 404 with `reverse_proxy api:8000` for `/api` and `/api/*` — no prefix stripping, because Django is mounted at `/api/...`. The image-level `apps/web/Caddyfile` is unchanged, so the reusable static frontend image is preserved.
- **IMPLEMENTED** — Gunicorn remains the application process: the image entrypoint is not overridden, and container startup never runs migrations or seeds (both remain explicit one-shot operator actions; release orchestration is a later slice).
- **IMPLEMENTED** — operator PostgreSQL backup/restore primitives (manual, on-demand; no automation, no Compose startup hook): `deploy/scripts/postgres-backup.sh` (live logical backup of the configured application database while the stack keeps serving: `pg_dump -Fc` custom-format archive written host-side as `<final>.partial`, published by atomic rename only after non-empty + `pg_restore --list` parse validation staged through the pinned `db` container, then a self-verified SHA-256 sidecar in `sha256sum` format; umask 077 → 0600 artifacts; no host port, no host PostgreSQL client, no stack interruption; on failure no final-looking artifact remains and the partial is removed; the output directory must exist and must never be the repository) + `deploy/scripts/postgres-restore-empty.sh` (restores such an archive ONLY into an EMPTY target database: SHA-256 sidecar verified host-side before any Docker interaction, archive parse-validated, target emptiness enforced by user-schema relation/function counts with a hard refusal — clear message, zero changes, non-zero exit — on non-empty targets, then `pg_restore --exit-on-error` into the bootstrap-created existing database with no `--clean` / `--create` / `--force` / destructive bypass and no `--no-owner` / `--no-acl`; post-restore relation count reported; both scripts accept an optional `--project-name` for stacks started under a non-default Compose project name, defaulting to the project declared in the Compose file). Boundaries: logical recovery point only (no PITR/WAL), single-database scope (no `pg_dumpall` — the application role is runtime configuration), no scheduling/rotation/off-host/encryption, no destructive in-place cutover. Operator procedure: `docs/living-lab.md` (PostgreSQL logical backup and restore); script tests: `scripts/tests/postgres-backup-restore.test.sh`.
- **NOTE (temporary local topology bridge)** — the loopback gateway is plain HTTP for local acceptance, while `config.settings_production` enforces the same-origin HTTPS contract (`SECURE_SSL_REDIRECT` + `SECURE_PROXY_SSL_HEADER`). The deploy Caddyfile therefore injects `X-Forwarded-Proto: https` toward `api` (the api port stays private to the Compose networks, so untrusted clients cannot reach Django directly and forge that header). This is explicitly a LOCAL-ONLY bridge, not the public deployment contract: Secure session/CSRF cookies and HTTPS-only trusted origins make authenticated browser use impossible over plain HTTP, so the loopback surface is for operational acceptance (SPA delivery, `/api` routing, health, database persistence). The public slice terminates real TLS at this same gateway (ACME/HSTS belong there).

Compose schema/interpolation was validated with `docker-compose config` (Compose v5.5.0), including the fail-closed check that every required variable is rejected when absent, and the api healthcheck script was executed locally against a stub server (200 → healthy, 404/refused → unhealthy, with the required `Host` + `X-Forwarded-Proto: https` headers asserted).

## Production image publication (GHCR)

Canonical operational reference: `docs/living-lab.md` (Production image
publication).

- **IMPLEMENTED** — `.github/workflows/publish-images.yml` (`Production image publication (GHCR)`): on every COMPLETED and SUCCESSFUL run of the canonical Core verification workflow — its exact top-level `name:` value, `Core verification` — for a `push` to `main` (a `workflow_run` dependency by workflow name; renaming that `name:` requires updating the publication workflow's `workflows:` list. The publication workflow re-runs no test suite and verifies nothing by itself), it publishes exactly two production images to GitHub Container Registry, one per deployable artifact: `ghcr.io/<owner>/<repo>-api` (existing `apps/api/Dockerfile`, context `apps/api/`) and `ghcr.io/<owner>/<repo>-web` (existing `apps/web/Dockerfile`, repository-root context). The production Dockerfiles are unchanged; both images are built with Docker Buildx (official, SHA-pinned Docker actions) on pinned `ubuntu-24.04` runners, and the image repository names are derived from the repository identity at runtime: a Bash step on the runner lowercases `github.repository` and writes the immutable `ghcr.io/<lowercase-owner>/<repo>-{api,web}` reference to `GITHUB_OUTPUT` (no owner/repository is hardcoded, and no unsupported expression-level lowercasing is used).
- **IMPLEMENTED** — immutable tag contract: the ONLY tag on both images is the exact 40-character Git commit SHA of the verified commit (`ghcr.io/<owner>/<repo>-api:<40-char SHA>` / `...-web:<40-char SHA>`); no `latest`, branch, short-SHA, or timestamp tag is ever published. The source revision is the core run's `head_sha` (for a push to main: the pushed commit — the same revision the gate verified); each job checks out exactly that revision (explicit `ref:` + a `git rev-parse HEAD` assertion step) and stamps it as the standard OCI label `org.opencontainers.image.revision` alongside `org.opencontainers.image.source` / `.repos`. BuildKit provenance attestation is embedded in each published image (signed with the job's `GITHUB_TOKEN`; no extra permissions required).
- **IMPLEMENTED** — trigger + gate boundary: automatic publication is `push` to `main` only, and only after the core gate passed for that exact commit — a failed, cancelled, pull-request, dispatch, or non-main core run publishes nothing (both jobs skip via a visible job condition). The two jobs run in parallel and BOTH must succeed for the publication run to be green; a revision is deployment-ready only when BOTH image artifacts exist. Platform contract: `linux/amd64` — the documented VServer target (`deploy/compose.production.yaml`); every base-image digest in both Dockerfiles was verified against the registries to be a multi-platform index carrying linux/amd64.
- **IMPLEMENTED** — authentication + permissions: GHCR login with the runner's `GITHUB_TOKEN` only (no PAT, no repository secret, no long-lived credential); workflow permissions are exactly `contents: read` + `packages: write`. No BuildKit cache is configured (cold-cache builds are the verified contract; a GHA cache would require `actions: read/write` beyond the minimum publication envelope). No cancellation is introduced: the core gate already serializes pushes to main (queued, never cancelled), so superseded commits never publish in parallel, and republishing one head SHA is idempotent.
- **IMPLEMENTED** — Compose compatibility: the published references are exactly the values for the existing required variables `FG_API_IMAGE=ghcr.io/<owner>/<repo>-api:<full SHA>` / `FG_WEB_IMAGE=ghcr.io/<owner>/<repo>-web:<full SHA>`, consumed by `deploy/compose.production.yaml` unchanged (no image name is added to Compose; no mutable tag anywhere in the contract).
- **IMPLEMENTED** — static workflow contract test: `scripts/tests/publish-workflow.test.sh` (trigger, gate condition, minimum permissions, SHA-pinned actions, head-SHA checkout + revision assertion, GITHUB_TOKEN-only authentication, existing Dockerfiles/contexts, linux/amd64 platform, full-SHA-only tags, lowercase GHCR names, OCI labels, Compose compatibility; optional actionlint pass).
- **NOTE** — publication is NOT deployment: the workflow builds and pushes registry artifacts only. It touches no server, no VServer, and no Compose stack — no migrations, no TLS, no backups, no release command.
- **NOTE** — GHCR package visibility is not derivable from repository code (it is a repository/package setting outside this slice). If the created packages are private, the later VServer bootstrap must configure a minimal pull credential; this slice introduces no credentials and does not guess the visibility.
- **NOTE** — GitHub-hosted publication is pending external acceptance: the workflow is statically verified (YAML parse + contract test) and the local production build inputs were re-verified in this slice (see `docs/living-lab.md`), but the first real `main` run must prove: publication run success, both images pushed, both tagged with the exact main commit SHA, and pullability of both full-SHA references where registry visibility permits.
- **NOT IMPLEMENTED (later deployment slices)** — VServer bootstrap + exact-SHA deployment, GHCR server-side pull authentication (if the packages are private), TLS/public hostname, explicit migrations/release orchestration, pre-deploy backup, scheduled/off-host backups, rollback, and deployment serialization.

## Account Invitations

Canonical domain reference: `docs/domain/account-invitations.md`.

- **IMPLEMENTED** — global account invitation foundation: `accounts.AccountInvitation` (stable `public_id` UUID, inviter, normalized invited email, one-way SHA-256 token digest, lifecycle state, created/expiry/accepted/revoked timestamps). The raw token is cryptographically random (`secrets`), single-use, **never persisted**, never in `repr`, never in list serialization or logs; it is returned exactly once by the creation response (e-mail delivery deferred).
- **IMPLEMENTED** — API (browser-authenticated, real CSRF enforcement, active accounts only): `GET /api/account-invitations/` (own invitations with effective state, no secrets, other inviters never listed), `POST /api/account-invitations/` (201 + raw token once; `400` invalid email), `POST /api/account-invitations/{publicId}/revoke/` (own + effectively pending only; non-leaking 404), `POST /api/account-invitations/accept/` (existing-account flow: resolves token by digest, requires normalized authenticated-user email == invited email, atomically sets `accepted` + `accepted_at` + `accepted_by`; 404 unknown/terminal, 410 expired, 400 mismatch).
- **IMPLEMENTED** — canonical normalization: trim + lowercase (shared helper); stored emails are normalized; User email storage format intentionally unchanged (no User-email uniqueness introduced).
- **IMPLEMENTED** — lifecycle centralized in the service layer: `pending → accepted | revoked | expired`; terminal states never reactivate; exactly 7-day lifetime; effective expiry (a pending row at/past `expires_at` behaves as expired everywhere and is persisted as `expired` by state-evaluating operations; no scheduler).
- **IMPLEMENTED** — existing-account guard on invitation creation: `POST /api/account-invitations/` for a normalized email that already belongs to a User (canonical trim + lowercase lookup shared with registration; active or inactive) is rejected with `409` + stable code `account_exists` before any token is generated or invitation is written; it takes precedence over `pending_invitation_exists` and creates no memberships. Already-existing invitation records for account emails are still redeemed through the existing preview/acceptance/registration flows (the guard restricts new creation only).
- **IMPLEMENTED** — duplicate-pending rejection (non-account emails): creating for a normalized email that has an effective pending invitation fails deterministically (`409`, stable code `pending_invitation_exists`, neutral message) and leaves the existing invitation and its token completely unchanged (no replacement, no revocation, no token/expiry/timestamp change); the existing invitation remains fully usable. Expired/revoked invitations never block: an effectively expired persisted-PENDING row is transitioned to `expired` by the creation operation, and the new invitation gets a fresh cryptographically random token with the normal 7-day expiry.
- **IMPLEMENTED** — structural invariants: unique `public_id`, unique `token_digest`, and a partial unique index limiting to one `pending` row per normalized email (migration `accounts/0003`).
- **IMPLEMENTED** — concurrency (real PostgreSQL row locks / constraints, threaded tests): concurrent acceptance of one token leaves exactly one `accepted` transition with `accepted_by` set once; concurrent creation for one normalized email leaves exactly one pending invitation and exactly one usable token — the losing creation fails deterministically with `pending_invitation_exists` (partial unique index serializes the inserts; the empty-row race resolves into the duplicate rejection).
- **IMPLEMENTED (guarantee, pinned by tests)** — acceptance creates no User and no `ResearchGroupMembership` / `ProjectMembership`; the token grants no access to any ResearchGroup, Project, Work Item, or Meeting (authentication ≠ membership; deny-by-default authorization untouched).
- **IMPLEMENTED** — invite-only registration redeems a valid pending invitation into exactly one new account: `POST /api/auth/register/` (`{token, username, password}`; a client-supplied `email` is rejected fail-closed) atomically creates the normalized-email `User` and marks the invitation `ACCEPTED` in one transaction bounded by the invitation row lock, then authenticates a normal revocable session. No public signup, no membership, no permissions; an existing (incl. inactive) matching normalized email blocks signup and leaves the invitation pending. Real Postgres concurrency coverage proves one token yields exactly one account. Canonical reference: `docs/domain/account-registration.md`.
- **IMPLEMENTED** — non-consuming invitation preview: `POST /api/auth/registration-invitation/` (`{token}`) reports whether a token is effectively pending (invited email, expiry, `accountExists`) without consuming it, without authenticating, and without disclosing the email for a terminal token (persists an effective `EXPIRED` transition).
- **IMPLEMENTED** — non-consuming registration password policy: `POST /api/auth/registration-password-policy/` (`{token, username, password}`; a client-supplied `email` is rejected fail-closed) evaluates the candidate password with exactly the configured Django `AUTH_PASSWORD_VALIDATORS` (via `get_default_password_validators()`) against the same transient candidate identity registration uses (client username + invitation-authoritative email) and returns `{valid, requirements: [{code, label, satisfied}], accountExists}` using Django's stable validation codes and each validator's configured help text. Strictly read-only (no row locks, no invitation lifecycle persistence — an effectively expired PENDING invitation is reported `expired` while remaining PENDING), no User/membership creation, CSRF-protected like register/preview; failed registration now returns the same `requirements` array (`{code, error, requirements}`). Canonical reference: `docs/domain/account-registration.md` §13a.
- **IMPLEMENTED** — frontend live password-policy validation in the Create Account flow: the new-account form evaluates the in-progress candidate through `POST /api/auth/registration-password-policy/` (debounced 300 ms on username/password changes, with a latest-request guard so stale responses never overwrite a newer candidate). The guidance block is hidden while Password is empty; once a value exists it renders only the authoritative verdict for the CURRENT candidate as compact 11 px/16 px rows with 14 px icons (6 px row gap) — a single “Checking password requirements…” line while the candidate is being checked, and a verification-error line (no stale rows) when the check fails. The four canonical validator codes render concise user-facing copy (“At least 8 characters”, “Not a commonly used password”, “Not entirely numeric”, and — failed only — “Password is too similar to your personal information.”); raw Django help text is never shown for them, and an unknown future code falls back to the backend-provided label so it is never silently hidden. A satisfied similarity rule renders no row (visible or accessible); a failed similarity rule renders a concise danger error row. State is carried by icon plus visually-hidden “Satisfied.”/“Not satisfied.” text — visible copy never appends state words — and the password field gets a danger state only when the authoritative result for the current candidate is invalid. The backend remains the sole source of truth for rules and verdicts (no validator logic is reproduced in the frontend), a failed live check keeps the button disabled without optimistic success, and a final registration `password` rejection reconciles its authoritative `requirements` into the live display. The form renders in a fixed 380 px content column (24 px page gutters outside the box), the password inputs reserve a 72 px trailing band, and the app’s 32 px reveal button sits in its own slot offset from the far-right band used by browser-native credential controls (no password-manager functionality is disabled).
- **NOT IMPLEMENTED (deferred)** — e-mail delivery, e-mail verification, password reset/recovery, membership invitations, invitation rate limiting, invitation audit history, global normalized User-email uniqueness, and account merging.
