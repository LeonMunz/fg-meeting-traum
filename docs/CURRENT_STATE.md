## Activity

Canonical domain reference: `docs/domain/activity.md`.

- **IMPLEMENTED** — Activity event foundation (persistence/domain only — no Activity API, no Home Activity rail, no feed rendering; Activity is an awareness/history stream, not a notification inbox). Activity events are the canonical persisted concept `audit_history.AuditEvent` (append-only, no update/delete path), recorded through `record_audit_event` **inside the same logical transaction** as the domain mutation: a rollback never leaves an orphaned event and a committed mutation always has its event (pinned by simulated post-mutation failure tests for create and update).
- **IMPLEMENTED** — Work Item event slice: one event per logical operation (domain-level action boundary, deliberately NOT one event per changed column) — `work_item.created` and `work_item.updated` with a structured, ID-based `data["changes"]` diff. The required action boundaries are reconstructable from the persisted event: **status changed** (`statusDefinition` from/to refs), **completed** — semantically distinct from an ordinary status change because the stored status summary now carries the fixed semantic `category` (`todo`/`in_progress`/`review`/`done`), so a transition into `done` (which drives the server-managed `completed_at`) is marked `to.category == "done"` with no join back to the StatusDefinition; a transition out of `done` is an ordinary status change, **assignee changed** (`assignees.added`/`assignees.removed` user refs), **due date changed** (`dueDate` from/to, including clearing to null). A no-op update records no event. Board drag/drop reuses the same contract (cross-column move = one `work_item.updated` with the status transition; pure within-column reorder = no event).
- **IMPLEMENTED** — structured-semantics rule: `event_type` is a stable machine code and `data` stores IDs + fixed enums (rendered names are display convenience, never the source of truth) — a later projection can answer WHO (actor FK) / WHAT (event type + structured changes) / WHICH (WorkItem FK or Meeting FK) / WHERE (Project + Research Group scope FKs) / WHEN (`created_at`).
- **IMPLEMENTED** — Meeting event slice (second real object type on the same `AuditEvent` concept; no second event table): one event per logical Meeting operation — `meeting.created` (both `create_meeting` and `create_meeting_from_series`; Series section snapshots and the default Agenda Section are internal structure, not events), `meeting.rescheduled` (a real `scheduled_at` change in one `update_meeting` = one event with structured `scheduledAt` from/to as UTC ISO-8601; a title-only or same-value update records no event — the title is not a tracked aspect), `meeting.completed` (`end_meeting` only; structured `endedAt`; Start/Reopen are not recorded), `meeting.agenda_item_added` (`create_meeting_item`; item id+title, internal `position` writes never appear), and `meeting.follow_up_scheduled` (`schedule_meeting_item_follow_up`; anchored to the TARGET Meeting with its Research Group/Project scope, structured `sourceMeeting`/`sourceItem`/`targetSection`/`targetItem` refs plus a stable flat `data["sourceMeetingId"]`; the internally materialized target item records no separate `agenda_item_added` event; an idempotent retry records no second event). All are recorded inside the same `transaction.atomic()` block as the Meeting mutation (pinned by simulated post-mutation failure tests for create, reschedule, complete, and follow-up); `update_meeting` is now transactional for that guarantee.
- **IMPLEMENTED** — Activity authorization rule: an Activity entry about an object is visible iff the user can read that object today (never a privacy bypass). Proven by the existing `GET /api/work-items/{id}/history/` enforcing the identical read rule as the Work Item itself (ProjectMembership owner/member/viewer + current ResearchGroupMembership; group admin without Project membership gets a non-leaking 404).
- **IMPLEMENTED** — permission-safe aggregate Activity read API `GET /api/activity/` (authenticated; Work Item slice events `work_item.created` / `work_item.updated` plus Meeting slice events `meeting.created` / `meeting.rescheduled` / `meeting.completed` / `meeting.agenda_item_added` / `meeting.follow_up_scheduled` plus Project slice events `project.member_assignments_resolved` / `project.ownership_resolved_for_offboarding` / `project.archived` / `project.restored` / `project.deleted` plus Research Group slice event `research_group.member_offboarded`). Read-time authorization: a Work Item event is returned only if the requester can read the affected Work Item today through the canonical Project read boundary — the identical rule of Work Item reads and per-Work-Item history (a Research Group admin without Project membership sees no private Project Activity); a Meeting event is returned only if the requester can read the affected Meeting today through the canonical `MEETING_READ` rule (creator-or-explicit-participant; group/Project membership, ownership, or admin status alone never grants Meeting Activity visibility); a `meeting.follow_up_scheduled` event is returned only while the requester can read BOTH the source and the target Meeting today, so target-only readability never leaks source Meeting metadata (the source reference is filtered in the database via the stable `data["sourceMeetingId"]` key); a Project event is returned only if the requester can read the affected Project today through the identical canonical Project read boundary (current ProjectMembership owner/member/viewer + current ResearchGroupMembership — the identical rule of Project reads; a Research Group admin without Project membership sees no private Project Activity either); archiving is not deletion — an archived Project keeps normal read authorization, and the archive state itself neither grants nor revokes; a `project.deleted` event (Project FK nulled by the deletion) is durably persisted but never returned — it fails closed and is never authorized from the retained research_group scope, actor, subject user, or payload; a Research Group event is returned only while the requester can read the affected Research Group today through the identical canonical group read rule (current ResearchGroupMembership — both the member and the admin role grant `GROUP_READ`, the identical rule of Research Group reads); losing group membership immediately removes the historical Research Group events, and the event's `subject_user` (the offboarded member) never grants access — subject identity retains nothing; Research Group deletion is not supported (the event's `research_group` FK is NOT NULL / RESTRICT), so a retained Research Group event always references an existing group whose current read authorization is evaluable; participant removal through the normal domain path removes matching historical events from the feed immediately. The permission filter runs in the database before bounded pagination (`?limit=` 1..100, default 50; `?offset=` non-negative with a hard bound; invalid → 400) on a deterministic reverse-chronological ordering (`-created_at`, `-id`), so inaccessible events leak no title, actor, context, event data, existence, count, or page behavior; the response is a bare page with no total count. The feed projection is structured (event id / machine `eventType` / `createdAt`, the existing audit/history actor representation, `subjectUser` — the user an operation acted upon (for Project events the resolved member / final owner; for `research_group.member_offboarded` the offboarded member), same user-ref representation as actor, null for Work Item / Meeting events and for Project events without one (never fabricated; event context, never an authorization input), affected Work Item id + current title or affected Meeting id + current title with the non-matching identity pair null, Project/Research Group context — null Project for group-scoped Meetings, the affected Project itself for Project events, the event's own Research Group with null Project for Research Group events — and the structured `changes` payload whose Work Item semantic `category` distinguishes a completion via `to.category == "done"`; for Project events `changes` carries exactly the allowlisted persisted payload keys of that event type, for Research Group events the allowlisted offboarding summary keys — never the raw `AuditEvent.data`); events of a hard-deleted Work Item, Meeting, or Project leave the feed while staying durable in the database (FK nulled via `SET_NULL`). The feed issues no per-event relation queries: every relation the serializer reads (`select_related` actor / subject user / Work Item / Project / Research Group / Meeting / the Meeting's Project / the Meeting's own Research Group / the event's own Project and its Research Group / the event's own Research Group) is eager-loaded on the page queryset, so the per-request query count is constant in the page's row count (one page query plus the session/authentication queries shared by every authenticated request).
- **IMPLEMENTED** — Activity feed fail-closed hardening for `meeting.follow_up_scheduled` source references: the stored `data["sourceMeetingId"]` is type-checked in the database before any numeric conversion (jsonb type check, then an arbitrary-precision numeric comparison against the readable-Meeting subquery), so a persisted malformed reference (missing key, JSON null, string, boolean, object, array, or non-integral number) excludes exactly that event — `GET /api/activity/` still responds successfully, no malformed row can fail the request or be coerced into another Meeting ID, and the dual-readability rule (source AND target readable today) is unchanged for valid references.
- **IMPLEMENTED** — Project and Research Group audit event persistence (pre-existing; predates the aggregate Activity feed work): recorded through the same canonical `record_audit_event` into `audit_history.AuditEvent` inside the same transaction as the domain mutation. Project events (`project` FK = the affected Project): `project.member_assignments_resolved` (assignment resolution during membership role change, membership removal, and Research Group offboarding), `project.ownership_resolved_for_offboarding` (ownership transfer for the offboarded final owner), `project.archived` (manual archive and Research Group offboarding archive), `project.restored`, and `project.deleted` (empty archived Project; the event is persisted before the Project row is deleted, so its `project` FK is nulled afterward). Research Group event (no `project` FK): `research_group.member_offboarded`. The Project events are durably persisted and **ARE** currently returned by `GET /api/activity/` under the read-time Project authorization rule above (Project Activity feed projection); the Research Group event **IS** currently returned by `GET /api/activity/` under the read-time group read rule above (Research Group Activity feed projection: visible only while the requester can currently read the group — `GROUP_READ`, both member and admin roles — and the event's `subject_user`, the offboarded member, never grants access; the structured offboarding summary is projected through the same allowlist mechanism). The nullable `subject_user` FK is set only by these pre-existing events, to the user the operation acted upon (the offboarded member, the member whose role/membership/assignments were resolved, the offboarded final owner); Work Item and Meeting events do not set it. Canonical reference: `docs/domain/activity.md` §4b.
- **NOT IMPLEMENTED (deferred)** — Home Activity rail/feed UI; Work Item deletion event; Meeting start/reopen/participant/Item-outcome/deletion events; further Research Group event families (only the pre-existing `research_group.member_offboarded` is projected today); and any notification semantics.


## Meetings

- **IMPLEMENTED** — Meeting scopes: **Research Group Meeting** (`group`, no Project) and **Project Meeting** (`project`, required Project), enforced by a DB check constraint.
- **IMPLEMENTED** — occurrence structure `Meeting → MeetingSection[] → MeetingItem[]`.
- **IMPLEMENTED** — standalone Meetings get a real default `Agenda` Section.
- **IMPLEMENTED** — MeetingItems belong to exactly one MeetingSection (NOT NULL).
- **IMPLEMENTED** — lifecycle `upcoming → live → completed` with explicit Start / End / Reopen actions; `started_at` / `ended_at` set by the server.
- **IMPLEMENTED** — canonical Live Meeting current pointer + item outcomes: `Meeting.current_meeting_item` (persisted `currentMeetingItemId`; OneToOne, `SET_NULL` when the item is deleted; may reference an item of any outcome) and `MeetingItem.outcome` (`not_discussed` / `done` / `follow_up` — `discussing` is NOT an outcome, legacy only). Changing current never mutates an outcome, and resolving an outcome changes current only through a documented advance rule. Focus (`POST /api/meeting-items/{id}/focus`, Live-only) accepts any outcome and changes only the current pointer. Done (`POST /api/meeting-items/{id}/done`, Live-only) does not require the target to be current; when the item was current at operation start, Done advances to the next later `not_discussed` item in canonical `Section.position`, `MeetingItem.position` order across Sections, skipping resolved items and clearing current when no later open item exists, without wrapping. Done on a non-current item leaves current unchanged. Reopen Done (`POST /api/meeting-items/{id}/reopen`, Live-only) accepts only `done`, changes its outcome to `not_discussed`, and preserves `currentMeetingItemId` exactly; it never advances, reconciles, or makes the reopened item Current. The legacy direct `POST /api/meeting-items/{id}/follow-up` outcome action remains implemented with its existing behavior. Start sets current to the first `not_discussed` item only if no valid current exists and never mutates outcomes; End is never blocked by the current pointer, allows remaining `not_discussed` items, clears `currentMeetingItemId`, and never mutates outcomes; reopening a completed Meeting sets current to the first remaining `not_discussed` only if current is null. Newly created (incl. spontaneous) items are `not_discussed` and never automatically current. Generic MeetingItem PATCH rejects both `outcome` and legacy `status`. Cancelling a concrete scheduled follow-up is a reversal and never implies Make current; Reopen Done rejects `follow_up` and never changes follow-up scheduling. Legacy data migrations (historical background): 0009/0010 mapped `open -> not_discussed`, `discussed -> done`; 0011 removed the `status` column, added `outcome` + the persisted current pointer, and mapped legacy `discussing` rows to the Meeting's current item + `not_discussed`.
- **IMPLEMENTED (DOMAIN + API; UI NOT WIRED)** — `MeetingItemFollowUp` stores a concrete scheduled continuation separately from `MeetingItem.outcome`, with required target Meeting, target MeetingSection, target MeetingItem, lifecycle status, creator, and timestamps. `POST /api/meeting-items/{id}/schedule-follow-up` accepts an explicit existing `targetMeetingId` and `targetMeetingSectionId`, delegates all writes to `schedule_meeting_item_follow_up`, and returns the compact concrete target trace; MeetingItem detail/list reads expose the same active trace as nullable `followUpSchedule`. Database constraints enforce a distinct source/target item and at most one non-cancelled follow-up per source item. The domain operation requires an existing upcoming target Meeting and an explicit visible Section belonging to it, reuses the canonical Meeting write permission and agenda append rules, and atomically creates a new `not_discussed` target item plus the trace, copies only the source title, and changes the source outcome only after persistence succeeds. If the source was current at operation start, that same transaction advances the source Meeting to the next later `not_discussed` agenda item across Sections, skipping resolved items and clearing current when no later open item exists; scheduling a non-current source leaves current unchanged. Identical retries reuse the active schedule without advancing current again; a different target returns `409 Conflict` pending a later Reschedule operation. Read-only `GET /api/meeting-items/{id}/follow-up-targets/` returns only existing, writable upcoming Meetings other than the source in `scheduledAt`, ID order, explicitly recommends the earliest valid same-Series Meeting, and embeds only each candidate's visible occurrence Sections. Section recommendation prefers a unique shared `sourceSeriesSectionId`, falls back to a unique exact current-name match, and remains null for ambiguous or missing matches. Discovery performs no writes. `POST /api/meeting-item-follow-ups/{followUpId}/cancel` cancels one concrete scheduled FollowUp by its FollowUp ID, delegates all writes to `cancel_meeting_item_follow_up`, and returns a compact result (`id`, `status`, `sourceMeetingItemId`, `sourceOutcome`, `targetMeetingItemId`, `targetItemDisposition` = `removed` when the generated target was deleted, `preserved` when it remains, with the surviving target ID when preserved); the typed frontend client (`cancelMeetingItemFollowUp`) exposes the same contract, and the **Live Cancel follow-up UI is implemented**: for a selected Live MeetingItem with an active concrete `followUpSchedule`, the detail pane shows the persisted scheduled destination plus a neutral `Cancel follow-up` action (available even while the source is NOT Current — no Make current required; never shown for ordinary open, Done, or legacy unscheduled `follow_up` items). Confirming opens a confirmation dialog identifying the destination (meeting · date, section); opening/dismissing the dialog mutates nothing. On success the canonical Meeting + items are refreshed with the existing refresh pattern, the source remains Selected and now reads open/`not_discussed` without the scheduled destination, the server Current is rendered as-is (a non-null Current stays on the other item, a null Current stays null; no advance, no Make current, no automatic navigation), and no resolve/advance logic runs. When `targetItemDisposition = preserved`, a browser-visible informational notice tells the user the agenda item in the destination meeting was kept because it had already been changed. On failure (target no longer upcoming, permission/domain error, network) the dialog stays open with the standard error treatment and source/Selected/Current are untouched. Reschedule, Previous Context UI, automatic lifecycle transitions, Meeting creation, system Follow-ups Sections, and Topic persistence are not implemented. The domain-level `cancel_meeting_item_follow_up` operation IS implemented (see `docs/domain/meetings.md` §18a); its API endpoint, typed client, and Cancel Live UI ARE implemented. The existing direct `POST /api/meeting-items/{id}/follow-up` outcome action remains implemented and unchanged during the client migration.
- **IMPLEMENTED** — Live Meeting Selected-vs-Current UI: in a Live Meeting the agenda rail's *Selected* item (the item the user is viewing) is decoupled from the persisted *Current* item. Every agenda row is selectable regardless of outcome; clicking a row only changes the local (never-persisted) selection and the detail pane renders the selected item's content; the rail independently marks the actual current item ("Current" badge) and the selected non-current item ("Selected" badge); "Return to current" re-points the selection only. Selecting never moves the current pointer, never mutates an outcome, and calls no domain API. After successful Done or concrete follow-up scheduling of the selected Current item, the client refreshes canonical Meeting and item state and follows a non-null server Current; when the server clears Current, the resolved source remains Selected so its detail stays visible. Reopen Done refreshes canonical Meeting and item state while preserving the reopened item as Selected and preserving the server's unchanged Current, so "Return to current" remains available when they differ. Failed resolutions and ordinary refreshes do not move Selected. Start/reopening a completed Meeting continue to follow their returned Current. Done and scheduling controls render only while the viewed item IS the current item; the neutral Reopen control renders for a selected Done item that the user can act on. There is NO per-row Focus / make-current affordance in the Live rail; a deliberate "Make current" action is implemented in the selected-item detail context: while viewing a non-current item, the user can explicitly make that item the Meeting's persisted current item via the existing canonical Focus API (`POST /api/meeting-items/{id}/focus`, which accepts any outcome and changes only the current pointer); after success the local selection and the persisted current pointer converge; the agenda row itself remains selection-only; the Focus API remains implemented and unchanged.
- **IMPLEMENTED** — Meeting read access is creator-or-participant: a user may see/read a Meeting iff they created it or are an explicit `MeetingParticipant`. Research Group membership, Project membership, ownership, or admin status alone do NOT grant Meeting visibility. A Meeting invitation grants Meeting read access only (no Research Group/Project membership or permissions). The creator and any existing participant may add further participants; the added user may be any existing application user without Research Group or Project membership. Adding a participant does not create or alter Research Group membership, Project membership, or unrelated permissions. Read-only participant-candidate search is available for standalone Meeting creation and Meeting Template occurrence creation, gated by the corresponding create permission and intentionally unfiltered by Research Group or Project membership; the frontend create picker is not yet wired.
- **IMPLEMENTED** — Meeting deletion: `DELETE /api/meetings/{id}/` permanently removes one occurrence and its Meeting-owned Sections, Items, Participants, and Work Item origin links. Server-side scoped write authorization (group admin / project owner+member, archived read-only). Canonical Work Items, Meeting Templates, and sibling occurrences are never deleted.
- **IMPLEMENTED** — occurrence Section editing: add / rename / edit / hide / reorder (one-off Sections never touch the Template).
- **IMPLEMENTED** — permission-filtered Meeting lists (creator or participant); group Meetings do not expose private Project data.
- **IMPLEMENTED** — persistent `MeetingNote` owned by exactly one `MeetingItem`: canonical author from the authenticated request (not client-spoofable), non-empty content, deterministic ordering, CASCADE on MeetingItem/Meeting deletion. Add/Edit/Delete reuse the Meeting write model and are Live-only (Upcoming and Completed reject authoring); Completed Notes are read-only protocol that survive reload. Notes are embedded in the Meeting items list (no N+1). Meeting Note != Work Item (no Project/status/assignment).
- **IMPLEMENTED** — canonical Note → Work Item: the composer's `Create work item` persists the Note first and opens the Work Item dialog anchored to that exact persisted Note (never open simultaneously; failure keeps the draft). One primary WorkItem per Note, enforced by a unique constraint on `MeetingItemWorkItem.meeting_note` plus a transactional pre-check. Group Meetings require an explicit Project choice (no silent preselect); Project Meetings preselect their writable Project. Definition IDs are validated server-side against the selected Project. Deletion is safe both ways (Note/WorkItem/MeetingItem/Meeting deletion keeps the other side; only the link row disappears).
- **IMPLEMENTED** — Linked work is rendered directly at the source Note (title, Project, assignees, status, permission-filtered) and opens the existing Work Item Inspector in place (Meeting context preserved); the Inspector shows `Created from` (Meeting, agenda item, source Note) resolved from the source relation. Unlinked Notes of Completed Meetings keep a quiet `Create work item` when the user can write the Meeting's scope.

## Home

Canonical domain reference: `docs/domain/home.md`.

- **IMPLEMENTED** — Home **Needs attention** Work Item candidate read model (backend read service `work_items.home_attention.get_work_item_attention_candidates`; read models unchanged — now exposed read-only through the Home aggregate API `GET /api/home/`; no Home UI, Activity untouched): for the current user, returns the user's own currently assigned Work Items that are open (status category not `done`) and overdue and/or blocked — overdue = canonical date-only `due_date` strictly before the current Django application-timezone date (due-today is NOT overdue), blocked = canonical non-empty `blockedReason` (foundation.md §11). Current read authorization is mandatory and identical to the personal My Work boundary (current ProjectMembership `owner`/`member` + current ResearchGroupMembership; stale assignment rows alone grant nothing — membership removal removes the item immediately). One candidate per Work Item with stable machine-readable reason codes `overdue` / `blocked` (an item that is both appears exactly once with both codes, overdue first). Deterministic ordering: overdue items before blocked-only items, earliest `due_date` first (NULLS LAST), Work Item ID tie-break. Candidate rows carry Work Item identity, title, Project identity/name, due value, semantic status category, blocked reason, and reason codes; no Home row limits, cross-domain prioritization, or summary counts are decided here.
